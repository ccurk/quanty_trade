产出是【知识】，每轮累积进台账——哪怕决策是 HOLD，知识也不许丢。

  - apply 后复检：重拉 current_code 再 grep 全清单 + diff 全量 config 纠

层2 服务端 _exp（职责收窄）：只放【当前在飞实验 + 下一预算窗队首】；

层3 git 台账分支（每轮可写——与持仓/运行状态无关，PATCH 被锁时它仍可写）：
  - 文件 LEDGER.md（仓库根），固定四节：锚点登记 / 已确认机制 / 候选队列 / 运行日志。

    → git push origin HEAD:"$LEDGER_BRANCH"（失败退避 2/4/8/16s 重试 4 次）
  - push 终败 → TG 报警"台账写入失败"，本轮增量压缩进下次 _exp carry 兜底；
    连续 2 轮终败 → 🆘（双持久层同时不可用）。
  - 原子纪律（本协议的核心）：任何 config/代码改动落地后，必须【同一轮】完成
    台账登记并 push 成功；未成功 = 改动流程未完成。下一轮发现"改动在飞但
    台账无记录"（diff config/current_code 对照台账发现无主改动）→ 先补记、
    再做任何新动作；无主改动无法归因时按可疑处理，走快速档回滚评估。
  - 重建条款：LEDGER.md 丢失/损坏 → 锚点登记节从 current_code
    grep -E "S[0-9]+ @20[0-9]{2}" 反向重建；已确认机制/候选队列从 audit 的
    _exp 历史重建；重建本身写运行日志 + TG 注明。重建期间=台账保守模式。
主流程并入次序：Step 2 拉数 → 读台账 → Step 3/4/4.5 → Step 4.6 归因（对照

## 设计要点（给人看的，不进 prompt）

1. **为什么三层**：容器无状态（v10 哲学7）→ 本地文件不可信。层1 锚点живет在
   服务端 current_code 里（平台存储），层2 _exp 在平台 config/audit，层3 git 在
   GitHub 远端——三层全是服务端权威，任意一层丢失都能从另两层重建。
2. **为什么 git 是主台账**：_exp PATCH 被平台锁死在"空仓+停机"窗口（2026-07-22
   实测：有仓时 bookkeeping 都写不进去），而 git 分支任何时刻可写、无大小限制、
   自带版本历史。_exp 退居"在飞实验状态机"，知识库走 git。
3. **"丢第一处"的三道闸**：①改动基底强制现拉 current_code ②apply 前后动态
   锚点 grep（台账驱动，改动越多清单越长，保护越强）③同轮登记原子纪律 +
   下轮无主改动巡检。
4. **E7 是本增补的实质放权**：v10 里"按盈利归因改代码"属触发器清单外扩张 =
   只能 🔴 提案等人工。v11 给了证据门槛制的绿色通道（双窗共现 + n≥30 +
   wr−be≥8pp + 跨轮复现），既满足"要进攻"，又挡住把噪音固化成代码的自伤。
5. **首轮引导**：台账分支不存在时从本分支（claude/jolly-bardeen-sz6d04）的
   种子 LEDGER.md 迁入；种子已按 2026-07-22 08:11Z 巡检的真实状态填好。
